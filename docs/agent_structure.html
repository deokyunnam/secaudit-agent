도구 10종은 감사 업무 4단계에 나뉘어 있습니다

왜 하나로 합치지 않았나

1

판정 근거와 참고자료는 도구부터 갈라야 섞이지 않습니다

검색 도구가 하나면 OWASP 문서가 ISMS-P와 같은 무게로 섞여 나옵니다. 컬렉션과 도구를 나눠 두어야 참고자료 결과 앞에 "판정 근거 아님"을 코드로 붙일 수 있습니다.

2

승인은 도구 단위로 걸립니다

gate는 도구 이름이 RISKY 목록에 있는지로 판단합니다. 조회와 격리가 한 도구 안에 있으면 조회할 때마다 승인을 받거나, 격리를 승인 없이 하게 됩니다.

3

번호 조회는 검색이 아니라 정확한 일치가 필요합니다

"2.6.2 원문"을 의미 검색에 맡기면 비슷한 2.6.1이 나올 수 있습니다. 번호를 아는 경우는 파일을 직접 여는 도구로 처리해 근거 추적 검사가 정확해집니다.

4

판정 규칙은 LLM이 아니라 도구가 계산합니다

승인 여부, 허용 포트 대조, 담당자 확인 대상 같은 판단을 도구 안에서 끝내고 결과만 넘깁니다. 일을 잘게 나눌수록 LLM이 추론할 몫이 줄어듭니다.

줄일 수 있는 후보 — 겹치는 부분이 있는 건 사실입니다.

  • list_unauthorized_mcp는 collect_mcp_inventory 결과의 부분집합입니다. "비인가만 짧게"라는 질문이 많아 따로 두었습니다.
  • get_isms_item과 get_kisa_item은 입력 형식으로 구분되니 get_criteria_item 하나로 합칠 수 있습니다.
  • 합치면 9→7종이 되지만 도구 설명이 길어지고 평가셋의 기대 도구도 바꿔야 해서, 이번 제출본은 그대로 두었습니다.
